# チェック役（PR を別の目で見る）

書いた窓が自分で green を付けない（自己採点しない）ための役。見る点はこの skill の 1 か所、判定の形は `scripts/verdict_form.py` が機械で見る。

## 立ち位置

- **read-only**: 直さない・commit しない・push しない。判定だけ。直しは書いた窓へ返す。Bash は読むのと物差しを回すのにだけ使う（`git fetch`・`git diff`・`git grep`・物差しの命令・`verdict_form.py`）。
- **見る点が読めない時は判定しない**: この skill が読めない時は判定を書かず「見る点が読めない（path）」の 1 行で止まる（見る点なしの green を出さない）。
- **別の目**: 判定を書くのは書いた窓と別の窓（レビューの窓）。助手（Agent）は立てた窓の中で動くので、助手の判定は立てた窓の session id で書く＝書いた窓が立てた助手の判定は書いた窓の判定と同じで、別の目にならない（`verdict_form.py` が `--writer` と照らして誤りにする）。判定を出す時は、守りの hook（guard の `pr_text`）が出す窓の本物の id を窓の環境の記録から読み `--reviewer` で渡し、1 行目の名乗りの字はその写しとして照らす（名乗りを作っても通らない）。書いた窓は PR の commit 全部の `Claude-Session:` の窓の組（途中の commit を書いた窓も書いた側）。PR 本文の `書いた窓:` と、merge でない commit の `Claude-Session:` の窓が、自分の session id と同じなら判定しない。名乗りが無い・両者が合わない時も判定せず `red（blocked: 書いた窓の名乗りが無い／合わない）` にする（green を出さない）。
- **都度取り直す**: 書いた窓の要約を信じない。依頼の本文（親窓が貼った物）と PR の今の先端を毎回取り直す。2 回目からは同じ PR の前回の判定のコメントだけを読み、前回の `[止める｜…]` が直ったかと、前回の `見た先端` から今の先端までの差分を見る。

## 手順

1. **差分を取る**: `git fetch origin main <枝> && git diff <積んだ基点 か origin/main>...origin/<枝>`（PR 本文に `積んだ基点:` があればそこから）。
2. **点で見る**（下の表）。依頼の「やる物」・完了の条件の各行を 1 行ずつ照らし、1 行ごとに所見を書く（問題なしも 1 行）。
3. **全体の絵と照らす**（点 13・下の節）。
4. **物差しを自分で回す**: 依頼の物差し（この repo なら `bash scripts/check_all.sh`）を PR の先端で回す。赤なら点 4 の fail（blocked ではない）。
5. **判定を PR のコメントに残す**（下の形）。出す前に `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/verdict_form.py" <下書き> --writer <書いた窓の組> --head <PR の先端>` で形を見る（書いた窓の組は `python3 "${CLAUDE_PLUGIN_ROOT}/scripts/pr_writer.py" --writers --head <先端>`（PR の repo の取り出しの中で回す。比べる元は道具が出所の今の main を聞いて決める＝手元の origin/main を渡さない） が `,` で並べて出す）（exit 0 で出す）。出す道具（GitHub のコメント）の前でも、守りの hook（guard の `pr_text`）が同じ道具を直に呼び、崩れていれば止める。
6. **返す**: green は依頼した窓へ、red は書いた窓へ直に 1 行（`判定 <PR> <枝>@<SHA12> verdict=green|red レビューした窓=<自分> 物差し=<最後の行>`、red は末尾に `直し=細目 §3「まず構造を疑う」`）。red の所見は直す行の一覧でなく根治の入口: 書いた窓は細目 §3「まず構造を疑う」で原因から直す。

## 見る点

| 点 | 見る事 | red になる時 |
|---|---|---|
| 1 依頼の充足 | やる物・完了の条件を 1 行ずつ・依頼文の範囲とオーナーの原文 | 欠け／頼まれていない物を足した（膨らみ）／急ぎや重さを理由に範囲・深さを削った（縮み）／依頼文の範囲が、依頼文に貼られたオーナーの原文より縮んでいる |
| 2 触った path | PR の差分の path（`git diff --name-only <基点>...origin/<枝>`・本文の手書きは見ない）と依頼の触ってよい path | その外を変えた／触らない path（変えない物）を変えた |
| 3 別の目 | 書いた窓 ≠ この窓 | 同じ・名乗りが無い（blocked） |
| 4 回帰 | 物差しを自分で回す・直した所の外の結果が変わらない | 物差しが赤／前から赤を「関係ない」と書いて名前を出していない |
| 5 秘密・顧客の物 | diff・PR 本文・ログ | 鍵・トークン・顧客の語・実データが 1 件でも在る（所見には場所だけ書き、値は書かない） |
| 6 当て物・本番の効き目 | 試験が本物の口を通っているか・「直した」が本番の効き目で確かめてあるか | 固定値・mock・特定の入力だけ通す分岐・試験を通すための fallback で緑にした／「直した・反映した」を本番の効き目でなく保存した物・手元の環境・部品単体の緑で言っている／当て物で動かしただけを終わったにしている（暫定なら暫定と書き、恒久の直しを書いた窓へ返す） |
| 7 なくす物 | PR 本文の「畳んだ古い物」と依頼のなくす物 | 消すと言った物が残る／古い前提を残して切り替え（新旧の分岐・設定の切り替え）を足した／消した名を指す文書・設定・試験が残る（`git grep <消した名>`） |
| 8 歯と口・注入の試験 | 足した・変えた試験・hook・検査／根治と言う直し | 「守る物を壊すと赤・戻すと緑」が実証されていない（名前が在るかだけの空の検査も）／根治と言う直しに、直した誤りの類をわざと入れて仕組みが拒む試験（注入の試験）が無い・先端で通らない・回す口に載っていない／回す口（CI・物差し・hook の登録）が無い・書いていない・書いた口が実際には呼ばない（口の側を読んで照らす） |
| 9 文書の事実 | 書いた path・名・URL が在るか | 無い物を在ると書いた／推し量りを事実として書いた／「概ね」などで未達を丸めた |
| 10 退役・迂回・呼ぶ側 | 消した・退役させた仕組み／新しい関所／共通の仕組み（hook・skill・agent・scripts）の呼ぶ側と呼ばれる側／土台の「壊れる:」変更の 2 段（土台の CONTRIBUTING.md §8） | 消した仕組みが守っていた物が無防備になった（守備範囲を横に照らす）／新しい関所を別の入口・直書き・引数の抜け・同名の別経路で迂回できる／呼ぶ側と呼ばれる側の片方だけを外した・変えた（参照切れ）／土台で使う側の古い形を、新旧の両方を通す 1 段目と使う側が移ったのを確かめる前に外した（1 段目で `plugins/core/古い形.json` に行が無い・2 段目に `kaku.py olds` の出力が無い）（「土台の中だけ」と書いた変更の中に使う側の物が頼る形が在るのも） |
| 11 言語ごとの点 | 下の「言語ごとの点」の表の該当する行 | 表の点に当たる物が在る |
| 12 既定で止まる | 足した・変えた入口と出口（核 §3 の誤りが入れない形） | 知らない値・欠けた材料・表せない決まりで、止まらず黙って既定の値・近い形・前回の値で進む所が在る／選べる値の外が入る／決まりを手で写す段を足した／正しい道を通らずに外へ出せる／「確かめた」が記録（試験・証明）でなく申告だけ／片付かない物を原因の台帳へ向ける決まりの文が、決まった言い回しで台帳を指した後の句で打ち消す（「…の行にして、載せなくてよい」。試験は字の形で見分けない） |
| 13 全体の絵 | 合意した全体の絵と実物（下の「全体の絵と照らす」） | 実物の絵が合意した版と差がある（差を見せてオーナーに決めてもらう）／合意した絵が無い・合意の印が無い（先に絵を描いて OK を取る）／自分で描かず書いた窓の申告や PR 本文の絵で照らした／合意した絵を変えたのに版を上げていない・オーナーの決定の在り処が PR 本文に無い |
| 14 跡の残らない手順 | 機械で照らせない手順（道具の呼び出しに跡が残らず、頭の中で踏むだけの物。オーナーの決定 2026-11-19 でレビューが見る）を、PR 本文・会話の記録・台帳で 1 つずつ照らす: ①同じ原因の他の問題を探す助手に、原因の 1 文だけを渡したか（結論を渡していないか） ②挙げた原因を全部原因の台帳に入れ、終わりの報告の前に台帳を引いた結果を付けたか ③新しく「止める」決まりの前にオーナーの同意を取り、注入の試験を置いたか ④前の red を単発の手直しでなく原因の段から直したか ⑤着手前に、受けた申告（引き継ぎ・完了報告）を正本で確かめたか ⑥設計モードの「ほんまにできる表」が埋まる前に実装へ進んでいないか ⑦返し先が別の窓の窓の返事に、オーナーが読めない番号・id を中の言葉として出していないか（オーナーがその窓を開けば読む） | 当てはまる手順の跡が PR 本文・記録・台帳のどこにも無い／跡が手順と食い違う（当てはまる手順が無ければ N/A） |

依頼に書いていない所の気づきは `[台帳へ｜…]` にする（止めない）。ただし点 4・5・6・8・10・11・12・13・14 は依頼に無くても `[止める｜…]` にしてよい。

## 全体の絵と照らす（点 13）

作り終わりに、実物が合意した全体の絵どおりかを別の目が確かめる段。差が無ければオーナーの一言なしで main へ入り、差があれば止めて聞く（細目 §7「main へ入れる」）。道具は docs-kit の skill big-picture の `scripts/big_picture.py`（下の `<docs-kit>` は入った docs-kit の根: 入った形では `${CLAUDE_PLUGIN_ROOT}/../../docs-kit/<この plugin と同じ版の dir>`、土台の repo では `plugins/docs-kit`）。

1. **合意した絵を引く**: `python3 <docs-kit>/skills/big-picture/scripts/big_picture.py pick <PR の repo の根> $(git diff --name-only origin/main...<先端>)` で、PR が触った file を覆う合意した絵を選ぶ（値の表 `docs-kit.big-picture.agreed`。1 repo に製品が複数ある時は製品ごとの絵の並びで、触った製品の絵だけが選ばれる。値が無ければ repo の根の `docs/全体の絵.json` 1 枚）。在り処が案件のページの名なら、そこから JSON を取る。exit 2（どの絵も覆わない file がある・絵が無い・値の形の誤り）、選んだ絵の `meta.kind` が `合意` でない・`meta.agreed` が無い時は fail（「絵が無い」＝先に絵を描いてオーナーの OK を取る）。N/A にしない。手順 2〜4 は選んだ絵ごとに回す。
2. **実物の絵を自分で描く**: PR の先端のコードと決まりを読み、合意した絵と同じ箱の id の言葉で、実物の絵（`meta.kind: 実物`・`drawn_from: <repo>@<先端の SHA12>`・`drawn_by: <自分の session id>`）を窓の作業場に描く。**書いた窓の申告・PR 本文の説明・PR が足した絵の JSON は使わない**（読むのはコードと決まりの実物だけ）。在るのに絵に無い物・絵に在るのに無い物を、そのまま描く。**粗さ**: 合意した絵に在る箱の間の流れは、コード（script・hook・skill の手順）が実際に配る・呼ぶ・読む物を全部描く（代表の 1 本で済ませない）。箱は合意した絵と同じ粗さで、絵に無い部品は 1 つの箱で足す。
3. **照らす**: `python3 <docs-kit>/skills/big-picture/scripts/big_picture.py compare <合意した絵> <実物の絵>`。exit 0（差なし）なら pass、exit 1（差あり）なら fail、exit 2（照らせない）なら fail（理由を書く）。docs-kit が入っていない・道具が回らない時は `red（blocked: 照らす道具が無い）`。
4. **所見に書く**: 差ありは `[止める｜設計]` で差の行（欄と箱の名）を全部写し、「main へ入れずに止め、差を見せてオーナーに決めてもらう」と書く（知らせて進めない）。差なしは点 13 に `pass（差なし・版 <合意した版>）`（絵が複数なら全部差なしの時だけ `pass（差なし・版 <名> <版>／<名> <版>）`）。
5. **合意した絵そのものを変える PR**: 版が上がり、PR 本文にオーナーの決定の在り処（日付と記録の名）が在る時だけ、変えた後の版と照らす。どちらかが無ければ fail。土台の plugin どうしの借りの矢印だけを足す版上げは、細目 §7「③の照らし方」が在り処になる（オーナーの決定を毎回は要らない）。

## 言語ごとの点（点 11・該当する言語だけ）

| 言語・対象 | 見る点 |
|---|---|
| Python | 例外の握り潰し（`except: pass`）で失敗を飲んでいない／副作用のある既定の引数／`subprocess` の `shell=True` に外の値を渡していない／型ヒントと実の返り値のずれ |
| JS・TS | `any` で型を消していない／`await` 漏れ（未処理の Promise）／`==` の意図しない型の変換／`catch` での握り潰し |
| Shell | `set -euo pipefail` の有無／未クォートの変数（`$x` → `"$x"`）／`rm -rf` の変数の展開先／pipe の途中のエラーが飲まれていない |
| SQL・DB | 戻せない migration（drop・truncate）に人の確認がある／N+1／index の無い全走査／トランザクションの境 |
| hook・検査（歯） | 点 8 の「壊すと赤・戻すと緑」／手元の home の設定にだけ繋がっていて、clone した所では 1 度も動かない形でない |

## 判定の形（PR のコメント）

```
レビューした窓: <自分の session id> 判定: green|red
見た先端: <見た PR の先端の SHA12>
job: <job>

## verdict
green / red / red（blocked: <なぜ測れなかったか 1 行>）
直し: 細目 §3「まず構造を疑う」（red の時だけ・blocked は除く）

## 点
- 1 依頼の充足: pass/fail（fail は 1 行理由）
- 2 触った path: pass/fail
- 3 別の目: 書いた窓 <id> ≠ この窓
- 4 回帰: pass/fail（物差しの最後の行）
- 5 秘密・顧客の物: pass/fail
- 6 当て物・本番の効き目: pass/fail
- 7 なくす物: pass/fail
- 8 歯と口・注入の試験: pass/fail/N/A
- 9 文書の事実: pass/fail/N/A
- 10 退役・迂回・呼ぶ側: pass/fail/N/A
- 11 言語ごとの点: pass/fail/N/A
- 12 既定で止まる: pass/fail/N/A
- 13 全体の絵: pass/fail（pass は `差なし・版 <合意した版>`・fail は差の数か「絵が無い」）
- 14 跡の残らない手順: pass/fail/N/A

## 所見
- [止める｜実装] path:関数 — 何が足りないか
- [台帳へ｜整地] 止めない気づき
- [直った｜実装] 前回の 2 番（2 回目だけ）

## 確認した範囲 / 確認していない範囲
- 見た diff・回した物差し / 見ていない所
```

- 札は `[止める｜<段>]`（直さないと出さない）・`[台帳へ｜<段>]`（通してよい。書いた窓が合流の前に各社の原因の台帳の行にし、PR 本文の「残り」に書く＝細目 §3）・`[直った｜<段>]`（前回の止めるが直った）。段は `設計`・`整地`・`見本`・`承認`・`実装`・`レビュー`（捕まえるべきだった段）。
- 点の値は上の雛形の行に書いた値だけ（点 1〜7 と 13 は `pass`／`fail`・点 3 は別の目の形・`N/A` は点 8〜12 と 14 だけ）。`verdict_form.py` が雛形の行から点ごとに読む（写さない）。
- `[止める｜…]` が 1 つでも在れば red、無ければ green（1 行目の `判定:` と合わせる）。
- `red（blocked: …）` は、コードを見た結果でなく測れなかった時だけ（物差しが環境で回らない・名乗りが無い）。
- `見た先端` が PR の今の先端と違う green は無効（見た後に push があった）＝今の先端で見直して判定を足す。
