# /spec-doc — 設計書の型を案件に起こす（規律→機構の実行経路）

**仕組み**（型ルールブックの「自己点検してね（規律）」を、スキルの実行 step ＋ fail-close ゲートに焼いたもの）

## repo ごとの値（config/skill-values.json）

repo ごとに違う値は、repo の根（`git rev-parse --show-toplevel`）の `config/skill-values.json` の `dev-flow.spec-doc.<鍵>` と `common.<鍵>` から読む。**鍵が無い・値が空なら右の既定で動く**。

| 鍵 | 使う所 | 無い時の既定 |
|---|---|---|
| `template_dir` | 型の一式（型ルールブック・生成コマンド `gen_spec_case.py`・gate `check_spec_doc.py`・config の schema）の置き場＝以下 `<型>` | 無し＝下の §型が無い repo で |
| `branch_rule` | 分かれ道を聞く時の正本 | 選択肢モーダルで 1 回聞く |
| `save_place` | 設計書を書く所・seal の後に残す所（行の並び） | 窓の scratchpad で書き、残す先はオーナーに聞く |
| `screen_design` | 画面の設計の持ち場 | 画面は別の設計に持ち、05 から指す |
| `decision_match` | 15 §6 の過去の決定との照合の口（行の並び） | 無し＝§6 に「未照合（照合の口なし）」と書く |
| `supersede_rule` | 覆した決定を墓標へ回す規律 | 15 の台帳の `supersedes` だけ |

## これは何か / なぜ要るか

「エージェントを替えても同じ設計書」を担保するための実行経路。治す病気は2つ ―― ①意図ドリフト（AI が曖昧な隙間を各々の既定値で埋める）②検証不能な出力（合格条件が無い）。型ルールブック（`<型>/型ルールブック.md`）は立派な**規律**だが、規律は読み手次第で守られない（規律案のみは構造欠陥・機構で強制せよ）。本 skill が、型を**作る/更新する行為そのものに機械の歯**を入れる。

- **設計書は「唯一の正解」**。コード・UI はそこから何度でも作り直せる派生物。設計が変わったら**設計書を先に直す**（living document）。
- 第一の読者は**作り手の AI**。人間語はその補助。迷ったら「人間に伝わるか」でなく「**AI が解釈で埋める隙間が残っていないか**」で判定する。

## 責務の境界

- **要件の合意の後段**。要件の合意 = 何を作るか合意（要件カード `REQUIREMENTS.md`・`/hearing` などが在る時はそれ）。spec-doc = その要件を型に流し込んで設計書一式にする。要件カードがある案件は step1 でそれを土台に使う。
- **この skill を回す窓はコピー/クラフト文言を書かない**（禁止事項）。設計書は「作る指示・意図・詳細・合格条件」まで。UI の具体コピーは各 specialist の 0→1 領域。
- 画面の設計は表の `screen_design` の持ち場。05 は画面区画を参照する（画面の中身を設計書に二重に持たない）。

## 発火条件

- 「設計書作って」「設計書の型で起こして」「仕様書を型で作って」「この案件の設計書を立てて／整えて」
- 要件の合意の後に「これを設計書に落として」
- 既存設計書の**更新**依頼（「設計変わったから設計書直して」）→ step4（更新フロー）へ

## skip 条件

- 設計書を要さない軽微修正・単発 UI 調整（型は「文書を増やすこと」が目的ではない＝右サイズ、P0 から刻む）。
- 既に型で LOCKED 済みの案件への軽い追記は step4 のみ（scaffold し直さない）。

## 型が無い repo で（`template_dir` が無い時）

型の一式（生成コマンド・gate）はこのプラグインに入っていない（型は repo ごとに持つ）。表の `template_dir` が無い repo では:
- Step1 の 2（生成コマンド）・各 step の機械チェック・Step3 の seal は回せない。Step1 の 1・3〜5 と Step2 の中身（原則の点検）は手で通す。
- 案件の dir は窓の scratchpad に `00_プロダクト宣言.md`・`01_憲法.md`・`02_業務要件.md`・`12_段階.md`・`13_受入.md`・`15_台帳.md` から右サイズで起こす（Step2 の各項の形で書く）。
- 渡す時は必ず「gate 未通過（型なし）＝形の機械の保証なし・中身は手で点検」と明記する。LOCKED にしない（`状態：Draft` のまま）。

## Step1 scaffold（生成コマンドで案件を起こす・右サイズで）

**着手前チェック**: scaffold の前に「**スコープ/設計の分かれ道が 2 通り以上あるか**」を数える。あれば `AskUserQuestion`（選択肢モーダル）で 1 回確定してから起こす（正本は表の `branch_rule`・外した時にやり直しになるかが判定軸。設計書は後段の全 P が乗るので、ここでの取り違えが最も高くつく）。

1. 配置先を決める（以下 `<設計書dir>`）: 表の `save_place` に在ればその行を上から読んで従う。無ければ窓の scratchpad の `<scratchpad>/<案件名>/設計書/` で書いて seal を回し、残す先はオーナーに聞く。保存先（PR の URL と repo 相対 path か文書の URL）を、次に頼む窓への依頼文に書く。
2. **生成コマンドで案件 dir を起こす**（フォルダを手でコピーしない＝型-層と案件-層の境界を生成の瞬間に刻む）:
   ```bash
   python3 <型>/gen_spec_case.py <設計書dir> --from <型>
   ```
   NN_*.md と `templates/` だけが案件へ入り、`_spec-instance.json`（生成 manifest＝これは案件という身元＋型の出自 version+hash）が書かれる。**gate 本体（check_spec_doc.py / 型ルールブック / _spec-template.json / test / schema）は案件に入らない**（唯一正本を canonical から参照実行＝gate 更新が drift しない）。型を素手でコピーして埋めると型モードが落とす（型を汚さない）。
3. ファイル名・本文の `〔　〕` を案件名で置換。`（例：…）` の見本は埋めたら消す。**`_spec-instance.json` の `case` を実案件名へ置換**し、採用しない番号は `na_docs` に `{番号:"N/A 理由"}` で理由付き宣言（seal の生成 manifest 健全性で検査）。
4. **右サイズを提示**（盲目的に全部作らない）: P0（`00/01/02/03/09/12/15` のうち案件に要るもの）から刻む。器・既存システムと重複する領域（認証・ホスティング等）は間引く。文書地図（型ルールブック §文書地図）に沿って、足りない番号は「必要になった段で足す」と宣言。
5. **出自 manifest `_spec-input.json` を作る**（この設計書がどこから来たかを機械で残す・seal で必須）: 要件の合意（`/hearing` など）を経た案件は `{"provenance":"hearing","hearing":{"requirements_ref":"…/REQUIREMENTS.md","version_or_hash":"…","req_map":{"REQ-01":["02_…","15_…"]},"unmigrated":0}}`（要件カードの各 ID→反映先文書の対応表＋**未移送0件**）。owner が hearing 不要と判断した直接発火は `{"provenance":"direct_fire","direct_fire":{"waived_by":"owner","reason":"…"}}`。要件がカードから設計書へ落ちきったかを seal 時に gate が照合する（要件脱落の検知）。

## Step2 guided authoring（P0 から・各 step に機械チェックを噛ませる）

P0 を順に埋める。**各 step で規律の"自己点検してね"を実行 step に変える**（穴を残したまま先へ行かない）:

1. **00 プロダクト宣言**: `① 誰が ② どんな困りごとを ③ 何をする道具で ④ 完成した姿` の**4要素**を1段落で宣言（"文書の説明"と混ぜない）。← 4要素が揃うまで先へ進まない。
2. **01 憲法**: 真の不変のみ（人間が最終判断／未確認を丸めない／秘密直書き禁止／外部送信限定／本番データ非破壊）。実装方式・UI表現・経緯を混ぜない（**層分離**）。
3. **02 業務要件**: 各 BUS を **1本2レジスタ**で書く ―「要はこれを作る（人間語1行）」→ すぐ下に「ID＋状態3軸＋Given/When/Then（AI語・測れる形）」を**隣接**。02 が最小 AC を持ち、詳細検査は 13。**禁止語を使わない**（測れない言葉は KPI か GWT に翻訳）。
4. **12 段階 / 13 受入**: PoC/MVP/本番を分け、各段階に受入条件（GWT）。
5. **15 台帳**: 未確定（UNKNOWN/PROVISIONAL）を本文から分離。決定は**状態3軸**（確からしさ6状態＋MoSCoW＋Production可否）。
6. **17 トレーサビリティ**（実装フェーズ入り前）: 全 Must 要件を横断接続。Must の空欄は「N/A: 理由」で埋める（黙って空けない）。
7. **per-case 意味検査 config を author**（案件に旧決定の変遷があるなら）: 決定台帳から `_spec-check-config.json` を起こす（schema/例 = `<型>/_spec-check-config.schema.json`）。旧文言の言い換え群を `dead` 正規表現に。**gate が config を実行時 schema 検証する**（必須キー `key/正解/dead/note`・`dead` 非空・正規表現の妥当性・未知キー禁止＝壊れた config は exit 2）。**15 台帳に `supersedes`（旧決定の差し替え）が在るのに config が無いと --lock で BLOCK**（旧意味残存を機械検査していない）＝意味検査が本当に不要なら `findings` 空 + `_about` に理由の config を置いて明示する。

8. **15 §6 決定照合**（seal の前・型の外の owner 決定との照合）: 表の `decision_match` に在ればその行を上から読んで従い（02 と 16 を連結して過去の決定と照合する口）、「ぶつかる」「Claude が読む」を 15 §6 に 1 行ずつ写す（扱い＝直した／覆す＝墓標へ／関係なし）。覆すと決めた決定は、旧決定を決定帳の墓標へ回す（表の `supersede_rule`）。照合の結果で seal は止めない（§6 が空なら --lock は警告だけ）。照合の口が無い・届かない時は §6 に「未照合（理由）」と書いて先へ進む（止めない）。

**各 step 後の機械チェック**（早期に落とす＝seal で一気に落とさない・§5 失敗モード注意）:
```bash
python3 <型>/check_spec_doc.py <設計書dir>
```

## Step3 seal（owner/他エージェントに出す前の fail-close 関門）

**緑でなければ handoff/LOCK 不可**。LOCK 相当の関門を `--lock` で通す:
```bash
python3 <型>/check_spec_doc.py <設計書dir> --lock
echo $?   # 0=PASS でなければ出さない（--lock は全 check を走らせる＝--key 併用は exit 2）
```
`--lock` が追加で強制するもの: **U4** 伝播未完（PROPAGATING 残）／**U6** P0核（00/01/15）存在／**U7** P0核の実質（未記入 `〔〕`・見出しだけ・02 状態3軸/15 台帳の実体が無い空 P0 を落とす）／**U8** 出自 manifest（`_spec-input.json` で hearing 由来 or 直接発火を宣言・要件未移送0）／**身元の境界**（`_spec-instance.json` の出自照合＝生成元の型 version+manifest_hash が現行 canonical と一致・古い型からの生成を BLOCK／生成 manifest 健全性＝case 置換済・adopted 非空・na 理由非空）。**未マーク案件（両 marker 無し）は --lock 不可**＝gen で起こすか §型ルールブック の backfill 手順で `_spec-instance.json` を付与。PASS すると合格証跡 `_spec-check-sealed.json`（gate 版・各文書 sha256・型出自）を出力する。**別リポ/別 agent へ渡した先は canonical 型 不要で `--lock` の代わりに `check_spec_doc.py <案件dir> --verify-receipt` で合格証跡を検証**（seal は型の正本に届く所で完結・下流は合格証跡を照らす）。
- **型を正当に編集した後**（型の持ち主の承認 + オーナーが git diff をレビュー済み）は身元を刻み直す: `python3 <型>/check_spec_doc.py <型> --stamp`（files/manifest_hash 再計算 + template_version bump・プレースホルダ全消失があれば拒否）。stamp を忘れると案件生成の出自照合が現行型とズレて --lock が落ちる（＝型改訂の反映漏れを検知）。
- 落ちたら: **違反は設計書を直す**（禁止語→翻訳／スナップショット語→更新ログへ移す／PROPAGATING→伝播しきる／`〔〕`→埋める／manifest→出自を宣言）。**誤検知は証跡台帳 `_spec-check-台帳.json` へ ALLOW を理由付きで記録**して再走（`reason/by/date` 空・`date` 非 YYYY-MM-DD は無効証跡＝BLOCK。1 証跡は 1 ヒットだけ許容＝同一 match の複数違反行を1行で飲み込まない）。
- gate が機械判定しない Gate4(例外耐性)/Gate6(環境)/Gate7(PoC)、および 02 の BUS ごと Given/When/Then 完全性・要件ID対応の意味整合は、型ルールブックのチェックリスト（規律）で人が確認（過検知回避で非機械化＝gate 出力末尾がこれを毎回告知する）。
- 緑 + ロック判定チェックリスト充足 + owner 再承認 → 文書全体を `LOCKED`。P0 核（00 等）のヘッダ状態欄を `状態：LOCKED` にする（確定でない間は `Draft` のまま）。LOCKED の後に直したら seal（`--lock`）を自分で再走する＝LOCKED を見張って自動で再走する仕組みは無い。
- **保証範囲の正直な明記**: 「エージェントを替えても同じ設計書」の機械保証は **`/spec-doc` を正しく完走し seal を通した経路** にだけ効く。skill を通さない別 AI・別経路が置いた LOCKED 設計書は機械では捕まらない＝受け取る側は `--verify-receipt` で合格証跡を照らす。
  - **緑の receipt が意味するもの**: 「受入条件・段階・テストが**在って空でなく、互いに繋がっている**」の形まで。中身を抜く変異でも `--lock` を通る経路が残る＝**緑の receipt を「中身を検査済み」の根拠にしない**。中身の"質"（GWT が本当に測れる形か・oracle が妥当か）は型ルールブックのチェックリスト（規律）で人が見る。
  - **「A ⊆ B」型の歯を足す時の作法**: 必ず「**A が空でないこと**」を同時に要求する。片方向だけだと「消せば通る」が必ず残る。

## Step4 更新フロー（設計が変わった時・living document）

1. **設計書を先に直す**（設計書が常に正）。
2. 決定を変えたら台帳（15）に伝播6項目（supersedes/affected_documents/migration_required/propagation_status/verified_by/effective_from）。反映しきるまで状態は `PROPAGATING`（CONFIRMED に上げない）。伝播表 = `templates/Decision変更伝播表.md`。
3. 要件（02）を変えたら対応する受入（13）も直す。
4. 旧文言が言い換えで残っていないかは per-case config の `dead` に足して gate で検出。
5. 各ファイル末尾の更新ログに1行。
6. seal（`--lock`）を再走して緑を確認してから配る。

## 渡し方（コピペ用・型ルールブック §渡し方）

> この案件の唯一の真実源は `設計書/` 直下の文書です。まず `00` を読み、文書地図と優先順位に従ってください。`01_憲法` は勝手に変えない（変える必要が出たら owner に確認）。状態が `UNKNOWN`/`PROVISIONAL` の項目を確定として実装しない。`Production Blocked` で本番出荷しない。

### 渡し方契約（★全体渡しが既定・設計ナビの内在ルール）
設計ナビ（設計書の型）は「エージェントを替えても同じ＝**丸ごと渡って初めて成立**」する前提で作られている。∴ **他 agent / 別 session へ渡す時の既定は「パッケージ丸ごと（設計書 dir ＋ 合格証跡 `_spec-check-sealed.json`）を渡し、受け手は 00 から入り文書地図・優先順位に従う」**。
- **章の部分指定で「これだけ読め」と渡すのは違反**（＝スコープ縮小の入口）。UI に効くのは 05/04/08 でも、要件(02)・ルール(06)・データ(07)・決定(15) 等を知らないと正しく作れない。
- 部分にする正当な理由があるなら、handoff 本文に**理由＋owner 承認**を明記する（黙って絞らない）。
