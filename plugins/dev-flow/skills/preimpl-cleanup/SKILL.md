# /preimpl-cleanup — 整地（書く側へ投げる前の棚卸し）

## 大原則（なぜ要るか）

目的は 1 つ: **改修で古くなる物を、本丸の作業を止めずに、片付け切る。** 書類を書くことは目的ではない。
**整地は、全部を分かっている頭（計画を出す側）が、直しを根治の問いで見つめ直して計画を出す段。道具で書かせない＝頭が書く。**
3 欄は根治の提案の型の 3 つの問いそのもの（下の §根治の 3 つの問い）。「畳む物」の行（`[同梱]`／`[後片付け]`）は、構造を変えたことで要らなくなる物（レビューする側が先端に残っていないかを見る）。
記録の置き場は PR 本文の 3 欄（repo の決まりがあれば表の `dev-flow.preimpl-cleanup.record`）。

> **A本線・B本線 両用の1本**：製品コード改修（A）でも仕組みの直し（B）でも同じこのスキルで整地する。

## repo ごとの値（config/skill-values.json）

repo ごとに違う値は、repo の根（`git rev-parse --show-toplevel`）の `config/skill-values.json` の `dev-flow.preimpl-cleanup.<鍵>` と `common.<鍵>` から読む。**鍵が無い・値が空なら右の既定で動く**（この SKILL の本文だけで整地ができる）。

| 鍵 | 使う所 | 無い時の既定 |
|---|---|---|
| `record` | 3 欄を置く所・照らす者 | PR 本文の 3 欄・レビューする側が読む |
| `past_sources` | 手順 2 の出典 | 過去の PR の整地の欄・`git log --grep` |
| `request_template` | 手順 4 の依頼文の雛形 | 依頼文に 3 欄をそのまま貼る |
| `cleanup_followup` | 手順 5 の「未」の行の行き先 | 次の片付けの PR の入力にする |
| `ledger` | 見張り（試験・検査）を足す・畳む時の台帳の書き方 | 足す物と畳む物を PR 本文に 1 行ずつ |
| `local_steps` | repo だけの段（受領証の箱・段の刻み方など） | 無し（読まない） |
| `common.rules.root_fix` | 根治の定義の repo の正本 | 下の §根治の 3 つの問い |
| `common.glossary` | 本文の語（頭・窓・job）の意味 | 語の一般の意味 |

## 根治の 3 つの問い（3 欄の中身）

1. **構造の原因** — なぜ起きたかを、リポジトリの構造／リポジトリ内のルール／AI への聞かせ方／AI に対するルールの聞かせ方 の観点から答える（目の前の症状でなく、それを生んだ形）。
2. **同じ原因から起きている他の問題** — 複数をはらむ前提で洗い出す。目の前の 1 件に絞らない。
3. **構造の変え方** — 「足す物」と「畳む物」。文を 1 行・見張りを 1 本足すことを中心に置かない（形を変えて要らなくなる物を畳む）。

repo の定義の正本があれば（表の `common.rules.root_fix`）そちらが勝つ。ここに言い換えを増やさない。

## 入力（走らせる前に握る）

| 入力 | 何を渡すか |
|---|---|
| `job_id` | この改修の仕事の名（PR 本文・枝の名と同じ字） |
| `change_kind` | `改修`（既存を直す）or `新規`（新しく作る） |
| この穴 | 止まり方と、なぜ起きたか（問い ①構造の原因で答える） |

## 手順

1. **構造の原因を書く**（1 欄）: 問い ①。
2. **同じ原因から起きている他の問題を洗い出す**（2 欄）: 問い ②。出典は表の `past_sources`（無ければ過去の PR の整地の欄の検索＝前に `[後片付け]` に回した行もここで拾う・`git log --grep`）。
3. **構造の変え方を書く**（3 欄）: 問い ③＝「足す物」と「畳む物」。畳む物は行頭 `[同梱]`（この PR で畳む）か `[後片付け]`（後の便）で 1 行ずつ（path・名前は `` `…` `` で囲む）。既定は `[同梱]`＝新しい物を足して古い物を残す形にしない（今の前提に書き換える・根の `CLAUDE.md` の核「直すは根治」）。`[後片付け]` にしてよいのは、畳む物がこの PR の触ってよい path の外にある時だけ（行に「他の窓へ回す」先を書く）。「念のため残す」「後で消す」は理由にならない。
4. **PR 本文に貼る**: 同じ dir の `整地受領証.template.md` の 3 欄（frontmatter と注記を除いた `## 1.`〜`## 3.`）を `## 整地（根治の 3 つの問い）` の下に書く。書く側へ頼む時は依頼文（表の `request_template`）に貼り、書く側は PR 本文の「何をどう変えたか」の後にそのまま載せる（書く側が自分で書いてもよい）。レビューする側が照らす（3 欄が在るか・雛形の `〔…〕` のままでないか・`[同梱]` 行の path が先端に残っていないか）。
5. **同梱の片付けの返し**: 書く側は PR 本文の 3 欄の `[同梱]` 行ごとに 済／未（理由）を書く。「未」の行は `[後片付け]` に書き換えて残す（表の `cleanup_followup`・無ければ次の片付けの PR の入力）。

## 3 欄の掟（照らすのはここだけ）

- 見出し 3 つ（構造の原因／同じ原因から起きている他の問題／構造の変え方）が在り、雛形の `〔…〕` のままでない事。書式・鮮度は見ない（頭が自分の理解で書く）。
- 見張り（試験・検査）を足す・畳むなら、表の `ledger` の書き方で同じ PR に入れる（無ければ足す物と代わりに畳む物を PR 本文に 1 行ずつ＝1 入 1 出）。

## 受領証テンプレ

正本は同じ skill dir の `整地受領証.template.md` の 1 枚（3 欄を PR 本文へ写す）。ここに写しを置かない。

## repo だけの段

表の `dev-flow.preimpl-cleanup.local_steps` が在る時だけ、その行を上から読んで従う（受領証を仕事の箱に作る・段を刻む等）。無い repo では読まない＝上の手順 1〜5 だけで整地は終わる。
