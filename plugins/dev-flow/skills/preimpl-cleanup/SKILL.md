# /preimpl-cleanup — 整地（書く側へ投げる前の棚卸し）

## 大原則（なぜ要るか）

目的は 1 つ: **改修で古くなる物を、本丸の作業を止めずに、片付け切る。** 書類を書くことは目的ではない。
**整地は、全部を分かっている頭（計画を出す側）が、直しを根治の 4 段で見つめ直して計画を出す段。道具で書かせない＝頭が書く。**
4 欄は根治の 4 段そのもの（下の §4 欄の中身）。「畳む物」の行（`[同梱]`／`[後片付け]`）は、構造を変えたことで要らなくなる物（レビューする側が先端に残っていないかを見る）。
記録の置き場は PR 本文の 4 欄（repo の決まりがあれば表の `dev-flow.preimpl-cleanup.record`）。

## repo ごとの値（config/skill-values.json）

repo ごとに違う値は、repo の根（`git rev-parse --show-toplevel`）の `config/skill-values.json` の `dev-flow.preimpl-cleanup.<鍵>` と `common.<鍵>` から読む。**鍵が無い・値が空なら右の既定で動く**。知らない鍵・畳んだ鍵・型の違う値は黙って捨てない（道具は名指しで止まり、窓の起動の時に guard が名指しで知らせる。表の探し方と鍵の一覧の正本は土台の `skill-values/`。鍵を足す時はそこへ足す）（この SKILL の本文だけで整地ができる）。

| 鍵 | 使う所 | 無い時の既定 |
|---|---|---|
| `record` | 4 欄を置く所・照らす者 | PR 本文の 4 欄・レビューする側が読む |
| `past_sources` | 手順 2 の出典 | 過去の PR の整地の欄・`git log --grep` |
| `request_template` | 手順 5 の依頼文の雛形 | 依頼文に 4 欄をそのまま貼る |
| `ledger` | 見張り（試験・検査）を足す・畳む時の台帳の書き方 | 足す物と畳む物を PR 本文に 1 行ずつ |
| `local_steps` | repo だけの段（受領証の箱・段の刻み方など） | 無し（読まない） |
| `common.glossary` | 本文の語（頭・窓・job）の意味 | 語の一般の意味 |

## 4 欄の中身

根治の 4 段（①問題 ②原因と同じ原因の他の問題 ③解決 ④未来）の定義・原因を探す所・誤りが入れない形・行き先・一時しのぎの中身は、土台の核 §3・細目 §3 だけが正本（ここ・型・値の表に写さない・repo ごとに変えない）。この skill が持つのは 4 欄の書き方と、3 欄の 5 つの穴の書き方だけ。

## 入力（走らせる前に握る）

| 入力 | 何を渡すか |
|---|---|
| `job_id` | この改修の仕事の名（PR 本文・枝の名と同じ字） |
| `change_kind` | `改修`（既存を直す）or `新規`（新しく作る） |
| この穴 | 何が起きたか（段 ①問題で答える） |

## 手順

1. **問題を書く**（1 欄）: 段 ①。渡された 1 件の症状を問題の幅にしない（誰が何に困ったか・本来どうあるべきだったか）。
2. **原因を書き、同じ原因の他の問題を別の目に探させる**（2 欄）: 段 ②。原因を 1 文に書いたら、その 1 文だけを読むだけの助手（Agent・`subagent_type: Explore`。自分の読みや直し方は渡さない）に渡し、repo 全体と関わる repo から同じ原因で起きている・起きうる所を場所つきの一覧で返させる。出典は表の `past_sources` も足す（無ければ過去の PR の整地の欄の検索＝前に `[後片付け]` に回した行もここで拾う・`git log --grep`）。返った一覧はそのまま 2 欄に載せ、原因と合わせて 1 つ 1 行で原因の台帳に入れる（書いた窓が削らない）。
3. **解決を書く**（3 欄）: 段 ③＝「足す物」「畳む物」「注入の試験と残る穴」。足す物は細目 §3 の誤りが入れない形のどれかで書き、2 欄の原因と一覧の全部に行き先（細目 §3）を付けて、各社の原因の台帳の行と合わせる（直す物を選ばない）。畳む物は行頭 `[同梱]`（この PR で畳む）か `[後片付け]`（原因の台帳の行にする）で 1 行ずつ（path・名前は `` `…` `` で囲む）。既定は `[同梱]`＝新しい物を足して古い物を残す形にしない（核 §3）。`[後片付け]` にしてよいのは、畳む物がこの PR の触ってよい path の外にある時だけ（原因の台帳の行にし、行に直す窓を書く）。「念のため残す」「後で消す」は理由にならない。注入の試験は、直す誤りの類を作り物でわざと入れて仕組みが拒む試験の名と回す口（書けない直しは根治と書かず、細目 §3 の一時しのぎの 3 つを書く）。5 つの穴（手で写す所／選べる値の外が入る所／知らない値・欠けた材料・表せない決まりで黙って進む所／正しい道を通らずに出る所／申告で済む確かめ）を 1 行ずつ 無し／塞いだ（どこで）／残る（理由。原因の台帳の行にする）で書く。
4. **未来を書く**（4 欄）: 段 ④。直した後、同じ問題と 2 欄の他の問題が起きない姿を、何が無くなり何が変わるか（作業する者の手順・オーナーの手・決まりの量）で書く。試験の名を並べる欄ではない。書けない時は 3 欄が足りていない。
5. **PR 本文に貼る**: 同じ dir の `整地受領証.template.md` の 4 欄（frontmatter と注記を除いた `## 1.`〜`## 4.`）を `## 整地（根治の 4 段）` の下に書く。書く側へ頼む時は依頼文（表の `request_template`）に貼り、書く側は PR 本文の「何をどう変えたか」の後にそのまま載せる（書く側が自分で書いてもよい）。振る舞いを変えない PR（誤字・記録だけ・版だけ等）は 4 欄の代わりに本文へ `整地: 不要（<なぜ要らないか>）` の 1 行を書く（訳はレビューする側が照らす）。4 つの見出しが在るか・雛形の `〔…〕` が残っていないかは、PR を出す前に守りの hook（guard の `pr_text`）がこの雛形を直に読んで照らし、欠ければ止める。レビューする側が照らす（4 欄が在るか・雛形の `〔…〕` のままでないか・`[同梱]` 行の path が先端に残っていないか・3 欄の注入の試験が先端に在り通るか）。
6. **同梱の片付けの返し**: 書く側は PR 本文の 3 欄目の `[同梱]` 行ごとに 済／未（理由）を書く。「未」の行は `[後片付け]` に書き換え、原因の台帳の行にする（細目 §3）。

## 4 欄の掟（照らすのはここだけ）

- 見出し 4 つ（問題／原因と同じ原因の他の問題／解決／未来）が在り、雛形の `〔…〕` のままでない事。書式・鮮度は見ない（頭が自分の理解で書く）。
- 見張り（試験・検査）を足す・畳むなら、表の `ledger` の書き方で同じ PR に入れる（無ければ足す物と代わりに畳む物を PR 本文に 1 行ずつ＝1 入 1 出）。

## 受領証テンプレ

正本は同じ skill dir の `整地受領証.template.md` の 1 枚（4 欄を PR 本文へ写す）。ここに写しを置かない。

## repo だけの段

表の `dev-flow.preimpl-cleanup.local_steps` が在る時だけ、その行を上から読んで従う（受領証を仕事の箱に作る・段を刻む等）。無い repo では読まない＝上の手順 1〜6 だけで整地は終わる。
