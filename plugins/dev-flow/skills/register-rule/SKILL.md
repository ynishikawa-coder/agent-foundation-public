# /register-rule — 規律を足す・直す前の関所

新しい規律・改訂を `CLAUDE.md`・`.claude/rules/`・共有の規律の置き場（表の `shared_rules_dir`）・`SKILL.md`・`references/` に書く前に必ず通す（書いた後の遡及チェックではない）。根治の型（3 つの問い）と常時読込の予算を、書く前の手順として通す。

## 対象の agent（引数）

`/register-rule [<agent>]`。省けば起動した agent。下の手順の「自前」「常時の規律ファイル」「on-demand の置き場」は対象 agent の物を読む。path はどれも agent の根からの相対。

agent ごとの「常時読込（自前）｜予算｜主な on-demand の置き場」は値の表の `agents_table` に在る（下の §repo ごとの値）。無い agent・無い repo では、その agent の `CLAUDE.md` §読む物 の「常時」「要る時」と、その `CLAUDE.md` が持つ予算の値を読む。予算の値はその agent が持つ（表は今の値の写しでなく、どこを見るかの道案内）。

## repo ごとの値（config/skill-values.json）

repo ごとに違う値は、repo の根（`git rev-parse --show-toplevel`）の `config/skill-values.json` の `dev-flow.register-rule.<鍵>` と `common.<鍵>` から読む。**鍵が無い・値が空なら右の既定で動く**（この SKILL の本文だけで規律の関所が回る）。

| 鍵 | 使う所 | 無い時の既定 |
|---|---|---|
| `agents_table` | §対象の agent の表（行の並び・Markdown の表） | 対象 agent の `CLAUDE.md` §読む物 |
| `shared_rules_dir` | agent を跨ぐ共有の規律の置き場 | 無し（根の `CLAUDE.md` だけ） |
| `db_id_check` | 外の DB の id を書く時に照らす台帳 | 無し（照らさない） |
| `desc_budget_bytes` | skill の description の合計の予算（Step 2.5） | 無し（測って PR 本文に書くだけ） |
| `session_start_payload_budget_bytes` | 起動時に差し込む文の予算（Step 2.5） | 無し（測って PR 本文に書くだけ） |
| `skill_count_cap` | skill の数の上限（Step 2.6） | 無し（上限なし・純増は PR 本文に理由を 1 行） |
| `learning_record` | 失敗・学びの書き先 | PR 本文の「学び:」の 1 行 |
| `dup_check_cmd` | Step 1 の機械の重複検査の命令 | 無し（grep だけ） |
| `entry_table` | 作業に結びつく規律の入口の表（指す 1 行を足す所） | 根の `CLAUDE.md` |
| `hook_places` | 見張り（hook）の置き場の分け方 | 対象 agent の `.claude/hooks/` |
| `subagent_contract` | subagent を足す時の約束 | 無し |
| `decision_record` | 原文・経緯を書く決定の記録の口（行の並び） | PR 本文に原文と経緯を書き、規律からは鍵で指す |
| `roster` | 規律と食い違いを照らす名簿 | 無し |
| `root_fix` | 提案の型の 3 つの問いの正本（`common.rules.root_fix`） | Step 3 の 1 の本文 |

## 書く前に読む

規律・設計書・依頼文・真因分析を起こす前に、次を Read で 1 度確かめる。
1. 関連の正本（`references/**`・`.claude/rules/**`・表の `shared_rules_dir`・schema）に同じ事が既に無いか（Step 1 と同じ道具）。
2. 頼む先の窓・エージェントの規約（触ってよい path・変更禁止・その箱の CLAUDE.md）。
3. 受けた根本原因の仮説は、採る前に関連ファイルを自分で読んで確かめる（`/verify` §1）。
4. 規律を改訂する時は関連 skill との矛盾を `grep -rn` で全部見る。矛盾があれば skill 側を直す（運用時に勝つのは skill）。
5. 外の DB の id を書く時は、それが箱の id か中身の id かを表の `db_id_check` の台帳と照らす（在る時だけ）。

省いてよいのは確かめの手間が起案の手間を上回る時だけ。規律・schema の改訂・依頼文・真因分析は省かない。

## 学びの記録

- 失敗・drift・学びは表の `learning_record` に書く（repo の md に積まない）。子窓は PR 本文と `send_message` の返しに「学び: <何が起きた／なぜ／次はどう防ぐ>」の 1 行を載せる。
- 確定したルール変更は学びでなく正本へ（下の Step で置き場を決める）。
- 同じ種類の失敗を 2 度起こしたら、規律の文を足す前に構造を疑う（Step 3）。

## Step 0: 目的寄与

書く規律・機構が `CLAUDE.md` 冒頭の目的（誰のために・何が達成されたら成功か・品質の定義）にどう効くかを 1 行で言えるか。言えない物は足さない（却下か保留）。棚卸しで何を削るかもこの物差しで決める。

## Step 1: 重複

表に `dup_check_cmd` が在れば先にそれを打つ（常時読込・同じファイルの他の節との重複と矛盾を照らす・止めない）。機械で決まらない物だけ grep で見る:

```bash
grep -rn "<語 1>\|<語 2>" CLAUDE.md .claude/rules/ .claude/skills/ .claude/agents/ references/ <shared_rules_dir> <repo の根>/CLAUDE.md 2>/dev/null
```

対象 agent の on-demand の文書（`agents_table` の右端）も同じ grep に足す。過去の失敗との重なりは `learning_record` を agent 名とキーワードで検索して見る。

ヒット 0 件＝新規／1〜2 件＝既存の改訂・拡張として扱う（新しく足さない）／3 件以上＝散っている＝Step 2 で 1 か所に寄せる。

## Step 2: 置き場

| 全動作に常時要るか | 既存 skill のどれにも属さないか | 置き場 |
|---|---|---|
| yes | yes | 対象 agent の常時の規律ファイル（`agents_table` の常時読込・最後の手段）。agent を跨いで共通なら根の `CLAUDE.md` |
| yes | no | その skill の `SKILL.md`＋常時の規律ファイルに指す 1 行 |
| no | yes | 対象 agent の on-demand の置き場（上の表）か `shared_rules_dir` の md（先に既存ファイルの更新で済むかを見る） |
| no | no | その skill の `SKILL.md` だけ（最も多い） |

- 迷ったら skill に書く。正本は 1 か所＝他の所は指すだけ（言い換えの写しも置かない）。on-demand に置く時は「いつ Read するか」（skill の Read の step・常時からの名指し）を同時につなぐ＝誰も読まない孤立ファイルを作らない。
- 作業に結びつく規律（試験を書く・依頼書を書く・commit 等、頭以外の窓も行う作業）は、正本を置いたうえで表の `entry_table`（無ければ根の `CLAUDE.md`）に「作業｜先に読む正本」を 1 行足す（足さないと書き手に届かない）。
- 見張り（hook）を足す時の置き場は表の `hook_places` に従う。共有の置き場に置くのは全 agent に無条件で効かせる物だけ。agent 固有の物は各 agent の `.claude/hooks/` に置く。
- ファイルを新しく足すのは、既存のファイルの末尾に足すと意味の座りが悪い時だけ。

### Step 2.5: 常時読込の予算（置き場が常時読込の時）

`wc -c` で測る（根の `CLAUDE.md`＋対象 agent の自前の常時読込＝上の表）。予算値は §対象の agent の表が指す所。根の `CLAUDE.md` や `shared_rules_dir` は自前の予算とは別の管理。
- 根の `CLAUDE.md` は全ての窓で毎ターン効く＝最も厳しく扱い、足したら弱くなった 1 行を削る。
- skill の description の合計（`desc_budget_bytes`）と SessionStart の注入（`session_start_payload_budget_bytes`）も同じ考えで測る。description は「何を・いつ使うか」の 1〜2 行。
- 足した後が予算を超えるなら、常時読込へ足さない。新しい規律を on-demand（skill・`references/`）に置いて常時は指す 1 行にするか、既存の常時の規律を 1 本以上 on-demand へ移して差し引きで収める。

### Step 2.6: skill を新しく作る時

1. 今の数を測る（`ls .claude/skills/ | wc -l`）。
2. 近い責務の skill・reference を grep で 1〜3 本挙げる。近い物が在れば、新設でなく統合を第一候補にする（reference の新設はこの手順が関所＝数の上限は無い・⟦鍵:規律/参照ファイルの数の上限なし⟧）。
3. `skill_count_cap` を超えるなら、統合する／1 本退役させて相殺する／owner の承認を取って cap を +1 する、のどれかを経る。黙った純増はしない。
4. `.claude/agents/*.md`（subagent）を足す時は表の `subagent_contract` に従う（在る時だけ・ハーネスとして作る・書く仕事は書く窓）。

## Step 3: 提案の型と規律の形

1. 中身は 3 つの問い（構造の原因→同じ原因の他の問題→構造の変え方・正本は `common.rules.root_fix` に在る時はそれ）に順に答える形で決める。文を 1 本足すことは③の細目であって、それ自体を直しにしない。規律を直す時は今の前提に書き換える＝古い文を残して例外や切り替えの文を足さず、古い文を書き換えるか畳む（根の `CLAUDE.md` の核「直すは根治」）。守らせたい事は、文でなく機械が止める形を先に考える。
2. **規律の文は今の結論（振る舞い）だけ**にする（⟦鍵:規律/規律の形⟧）。次の物は規律の文に書かない:
   - オーナーの原文・日付・出所（job・session・窓）・経緯・覆された旧い形（墓標）・外の文書の URL・長い ID
   - 「何が読める・どこに何がある」の事実（事実は変わる＝規律と食い違う）
3. **原文・経緯は決定の記録へ先に書き、規律からは鍵で指す**。鍵は `⟦鍵:<分野>/<名>⟧`（規律なら分野＝`規律`）。決定の記録の理由に鍵を、本文に原文（逐語）と日付・出所・経緯を書く。書く口は表の `decision_record`（行の並び・在る時だけ上から読んで従う）。無い repo では PR 本文に「⟦鍵⟧・原文・経緯」を書き、規律からは鍵で指す。

   - 原文は測れる条件や造語に訳して置き換えない。原文が無ければ推測で作らず聞く。
   - 決定を覆す時は、新しい行を書き（`置換元` に旧い行）、規律の文を今の結論に書き換える。旧い形は規律に残さない（経緯は決定の記録と git）。
4. 見張り（歯）を新しく足す時だけ、登録の前に変異体で確かめる（窓の scratchpad で手で行い、結果は PR 本文に 1 行）: 守る対象を壊すとその歯が赤くなるか（ならないなら空の歯＝登録しない）／その歯を外すと声が消えるか（消えないなら既に別の歯が守っている＝統合する）。安全の常設保証（秘密保護・破壊操作の人間確認・外部送信と staging の門）は根治の結果として畳まない。
5. 見張りを足す時は、それが原理の全面を覆うかを 1 行で書く（他の agent にも要るか／自分で実行する道も覆うか／隣の動詞・入口も覆うか）。incident の面だけで足りるなら、覆っていない面を PR 本文に書く。

## Step 4: 易化

書く文を読み返す。直す形: 専門用語が言い換えなしで 3 回以上出る／固有 ID・版番号を説明なしで置く／2〜3 段で済む話を 5 段以上に分ける／80 字以上の文が 3 文続く。直したらもう一度 Step 4。通ったら書く。

## Step 5: 書いた後の掃除

常時読込（根の `CLAUDE.md`・`CLAUDE.md`・`.claude/rules/*.md`・skill の description）を読み、次の 3 つを探す。何も無ければ黙って終わる。
- **重複** → 1 か所に寄せる案を出す（意味が変わる恐れがあれば寄せずに矛盾へ回す）。
- **死んだ指示**（使われていない機構・誰も指さない純文）→ on-demand へ移すか消す案を出す。名指しの参照（`§X`）が残る物は参照元も直す。
- **矛盾**・規律と正本（表の `roster`・決定の記録）の食い違い → 自動で直さず一覧にしてオーナーに○×を聞く。

常時読込の書き換えは PR の道で入れる（git の commit が巻き戻しの錨）。

## 出力の形

```
🔍 /register-rule <agent>
Step 0 目的寄与: <1 行> / 言えない → 足さない
Step 1 重複: N 件（<path:line>）→ 新規 / 改訂 / 集約
Step 2 置き場: <path>（常時要るか yes/no・skill 不属か yes/no）
Step 2.5 予算（<agent>）: 根 <B> / 自前 <B> / description <B> → 収まる / 棚卸し
Step 3 型: 構造の原因 / 同じ原因の他の問題 / 構造の変え方
       規律の文: 今の結論だけ（日付・原文・URL・ID 0）／決定の記録: <鍵> <在処>
Step 4 易化: OK / 直す
→ 書いてよい: yes / no
```

## よくある間違い

1. 既に常時読込に在る規律を skill にも詳しく書く → Step 1 で grep し、在れば指す 1 行にする。
2. 構造を見ずに歯を足す → Step 3 の型で構造の原因と同じ原因の他の問題を洗い出す。
3. 規律の文にオーナーの原文・日付・「〔墓標: …〕」を書く → 決定の記録の本文へ書き、規律は今の結論＋⟦鍵⟧。
4. 予算を超えたのに「対策だから」と常時読込へ足す → Step 2.5 で棚卸しする（移す・捨てない）。
5. 失敗の恒久対応を反射で常時の規律ファイルへ足す → Step 2 で「毎ターン要るか」を問う。多くは skill・checklist・`learning_record` で足りる。
