# /register-rule — 規律を足す・直す前の関所

規律・skill・hook を書く前に通す（書いた後の点検ではない）。

ミスから規律を足そうとしている時は、書く前に細目 §3「まず構造を疑う」で、守りたかった意図とのずれ（課題）から原因の段へ戻る（足す案が出た事が、根に届いていない合図）。

## repo ごとの値（config/skill-values.json）

`config/skill-values.json` の `dev-flow.register-rule.<鍵>` から読む。**鍵が無い・値が空なら右の既定で動く**。表の探し方・既定・知らない鍵の扱いの正本は土台の `skill-values/skill_values.py` の冒頭（「探し方」「照らし」）。

| 鍵 | 使う所 | 無い時の既定 |
|---|---|---|
| `dup_check_cmd` | Step 2 の機械の重複検査の命令 | grep だけ |
| `desc_budget_bytes` | skill の description の合計の予算（Step 4） | 測って PR 本文に書くだけ |
| `decision_record` | 原文・経緯を書く決定の記録の口 | 各社の CLAUDE.md が名指す決定の記録。名指しが無ければ各社の決定の記録（PR 本文で代わりにしない＝公開の repo の PR 本文は誰にでも見える） |
| `learning_record` | 失敗・学びの書き先 | 各社の CLAUDE.md が名指す原因の台帳の行 |

## Step 1: これは止める物か（最初に問う）

誰が決めるかの正本は核 §3 の最後の項（畳む・直す・言い換え・止めずに知らせる物は AI が入れ、新しく「止める」物と核の原則の変更はオーナーの同意）。ここに足すのは見分けの例だけ:

- 「止める」物の例: 返事や道具を止める hook・必須の検査・確認の段・人の手が要る段。同意は選択肢の画面で取る（核 §4）。
- 「直す」物の例: 死んだ参照・正本との食い違い。

- 安全の常設の守り（戻せない操作・秘密・deny）は畳まない。
- 守らせたい事は、止める前に「知らせるだけ」で足りないかを先に考える。

止める物かを決めたら、続けてその規律の根治の形を 3 つ書く（中身は核 §3・細目 §3）:

- **意図** — その規律が何のために在るか（誰の何を守るか）を、起きた事・原因と混ぜずに 1 文。書けない規律は足さない（守る物の無い規律）。

- **誤りが入れない形のどれか**（4 つの中身は細目 §3「誤りが入れない形」）— 文を足すだけで、どれにも当たらないなら原因の段へ戻る。
- **注入の試験** — その規律が防ぐ誤りの類を窓の作業場でわざと入れ、仕組みが拒む（赤・止まる）事と、外すと声が消える事を確かめる（消えないなら既に別の歯が守っている＝統合）。試験は回す口（CI・物差し）に載せ、結果を PR 本文に 1 行。

## Step 2: 重複

`dup_check_cmd` が在れば先に打つ。無ければ grep で見る:

```bash
grep -rn "<語 1>\|<語 2>" CLAUDE.md .claude/ plugins/ 2>/dev/null
```

0 件＝新規／1〜2 件＝既存の改訂として扱う（新しく足さない）／3 件以上＝散っている＝1 か所に寄せる。関連 skill と食い違えば skill 側も同じ PR で直す。

## Step 3: 置き場

| 効く先 | 置き場 |
|---|---|
| 土台（両方の AI） | 常時要る原則は `plugins/core/核.md`、AI の癖と逆を求める振る舞いの既定は `振る舞い.md`（核と一緒に毎回差し込む）、形・例は `細目/` の節の file、作業の手順は土台の skill |
| 各 repo の固有 | その repo の `CLAUDE.md`（常時）か、その repo の skill・文書（要る時） |

- 迷ったら skill に書く。正本は 1 か所、他は指すだけ（言い換えの写しも置かない）。
- 新しいファイル・skill は、既存の物の末尾に足すと座りが悪い時だけ。近い skill が在れば統合を先に考える。

## Step 4: 量と 1 入 1 出

- **1 つ足したら 1 つ以上畳む**（同じ PR で）。畳んだ物を PR 本文に書く。守りの数（guard の見張り・CI の検査・レビューの点。安全の守りは除く）は CI の `kaku.py grow` が main と比べ、増えたら赤。
- 核・振る舞いの既定は `python3 plugins/core/scripts/kaku.py check` で照らす（土台の中）。使う側の repo の `CLAUDE.md` は、plugin core の起動の hook が開いた時に照らして越えれば知らせる（使う側は kaku.py も数も写さない）。越えるなら常時へ足さず、細目・skill へ移して常時からは指す 1 行にする。
- skill の description は「何を・いつ使うか」の 1〜2 行。合計は `desc_budget_bytes` で測る。

## Step 5: 規律の形

1. 中身は Step 1 の形と注入の試験（核 §3）で決める。今の前提に書き換え、古い文を残して例外や切り替えの文を足さない。
2. 規律の文は今の結論（振る舞い）だけ。オーナーの原文・日付・出所・経緯・覆された旧い形（墓標）・「何がどこに在る」の事実は書かない。原文と経緯は `decision_record`（無ければ各社の決定の記録＝核 §8）へ。
3. 仕組みを消す時は、その試験と、消した物を指す文も同じ PR で消す。
4. オーナーの決定から直す時は、決定の記録のその行の `決まりへ` に直した file と PR を書く（決定が決まりへ戻る道は細目 §8「決めた事」の 1 本）。

## Step 6: 易化と書いた後の掃除

- 読み返して直す: 言い換えの無い専門用語・説明の無い ID・5 段以上の手順・80 字以上の文の連続。
- 書いた後、常時読む物（核・細目・`CLAUDE.md`・skill の description）を見て、重複は 1 か所に寄せ、死んだ参照は消す。食い違いは決定の記録が決めていればそれに従い、記録に無く意味が変わる物だけオーナーに聞く。
- 失敗・学びは根治の 5 段（核 §3）で `learning_record` へ（無ければ各社の原因の台帳＝細目 §3・核 §8。repo の md に積まない）。

## 出力の形

```
🔍 /register-rule
Step 1 止める物か: no（AI で入れる） / yes（オーナーの同意: <問いの窓>）
       意図: <何のために在るか 1 文> ／ 形: <誤りが入れない形のどれか> ／ 注入の試験: <何をわざと入れ・どこで赤／止まる・回す口>
Step 2 重複: N 件（<path:line>）→ 新規 / 改訂 / 集約
Step 3 置き場: 土台 / 各 repo の固有 → <path>
Step 4 量: 核 <B>・CLAUDE.md <B> → 収まる／足した <物> ・畳んだ <物>
Step 5 形: 今の結論だけ／原文と経緯: <在処>
→ 書いてよい: yes / no
```
