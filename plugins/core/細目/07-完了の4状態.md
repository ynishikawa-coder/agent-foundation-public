## 7. 完了の 4 状態

| 状態 | 意味 |
|---|---|
| 終わった | 終わりの条件と確かめの条件が全部そろった |
| 一部 | 合意した目標そのものが途中で止まった。残りは原因の台帳の行へ |
| 止めた | 決めた止まりの条件に当たって止めた |
| 続けられない | 技術・権限・構造の理由で続けられない |

- **根治の終わり** — 着手時に合意した成果と確かめ方で、その成果がそろったかを決める。合意した結果を変える時だけ変更点を示して合意し直す。目標の中の穴が結果や安全を妨げるなら未完。原因の台帳は根拠と行き先の記録で、状態だけで成果にしない。記録だけが残る時は「成果は確認済み、記録は未反映」と分け、成果を作り直さない。記録自体が依頼の成果か、安全な確定に必要な時はその範囲を未完とする。
- **報告の書き方** — 「ほぼ終わった」と書かない。最初に元の依頼への答えと根拠を書く。対策を入れた、普段の入口で結果が出た、相手が使えた、を依頼に応じて分ける。合意した結果を黙って狭めず、できない時は未達と次の一手を示す。別仕事はこの成果を止める依存だけ書き、外の穴は元の完了に混ぜない。原因の台帳に行き先を残し、オーナーの判断が要る時だけ、影響と AI の案を添えて聞く。
- **土台の直しの終わり** — 土台を直す仕事は、使う側の repo（製品の repo を含む）に残った同じ決まりの写し・古い形を指す文も、同じ仕事の中で直す（その repo の PR）。洗い出しだけで終わらせない。土台の PR は本文の「使う側の写しの残り」に、repo ごとの直しの PR か「なし（探した所）」を書き（名を公開できない repo は「ほかの使う側 <数>」）、その直しが全部合流するまで「終わった」と言わない。この窓から触れない repo は、原因の台帳の行にして repo ごとに 1 つの直す窓を `直す窓` に付ける。
- **main へ入れる** — 合流に伴う実際の効果を確認する。main への合流で利用者の通常の URL・本番処理・稼働中のエージェントに自動公開・配布されるなら、その影響まで合意済みかを確かめる。検証用のビルドだけでは本番公開にしない。合意の範囲内なら合流の前にオーナーへ「入れてよいですか」と聞かない。範囲外または効果が未確認なら、その合流だけ止め、準備・検証は進める。確かめる事は核 §7 の 1 行（使う側に届く誤りが無い事を、書いた窓と別の目で確かめる。機械で証明できる所は機械の緑がその確かめ）。別の目の判定は合流の前に今の先端で 1 回付ける（CI は結果を読み回し直さない。直した後は見直しで付け直す）。確かめが済み main と衝突が無ければ、書いた窓が自分で squash で入れる（人に merge の操作を頼まない）。全体の絵は設計の時に掘り下げる元の図（docs-kit:big-picture）で、合流の条件にしない。絵と違う・絵が無い・照らせないを理由に止めない。
- **設計図どおりかの照らし** — 合意した設計の仕事（案件・段の区切り）が全部終わった時に 1 回、AI が箱ごとに確かめ、完了の報告に「設計図どおり」か「差とその扱い」を 1 か所書く。PR ごとには照らさず、合意した絵の無い仕事は照らさない。作り方のずれは AI が設計どおりに直す（聞かない）。設計そのものを変える時だけ、絵に戻ってオーナーと合意し直す。
- **判定を頼む** — 書いた窓が別の目（核 §7）に判定を頼み、返しを受けて合流まで運ぶ。別の目は別の窓でも読むだけの助手でもよく、どれにするかは書いた窓が都度決める（どの窓が見たかは照らさない）。赤にするのは使う側に届く誤りだけで、届かない食い違い（PR 本文の数と中身の違いの類）は直す提案にする。
- **記録で確かめる** — 「確かめた」は申告でなく、後から誰でも読める記録（試験の結果・正しい道の証明・正本を読んだ出力）で示す。記録の無い確かめは未確認として書く。
- **別の道で確かめる** — 出した答えを、作った処理の出力や自分の報告で確かめない。生の正本（元のファイル・API・画面）を読んで照らす。
- **情報の取り方** — 結果は件数と失敗した物の ID だけ出す。50 件以上を見る時は script で数える。
