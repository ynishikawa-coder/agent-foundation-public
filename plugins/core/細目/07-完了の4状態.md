## 7. 完了の 4 状態

| 状態 | 意味 |
|---|---|
| 終わった | 終わりの条件と確かめの条件が全部そろった |
| 一部 | 合意した目標そのものが途中で止まった。残りは原因の台帳の行へ |
| 止めた | 決めた止まりの条件に当たって止めた |
| 続けられない | 技術・権限・構造の理由で続けられない |

- **根治の終わり** — 根治の仕事は、目標の中の台帳の行が全部 `直した` か `直さない` の時に「終わった」。台帳を引いた結果（行の数と行き先ごとの数）を報告に付ける。
- **報告の書き方** — 「ほぼ終わった」と書かない。終わりの報告は頼まれた物が終わった事と前→後を先に書き、外の穴ごとに何が穴か／放っておくと何が起きうるか／AI の案を添えて「どうしますか」と聞く（同じ原因の穴はまとめる）。
- **土台の直しの終わり** — 土台を直す仕事は、使う側の repo（製品の repo を含む）に残った同じ決まりの写し・古い形を指す文も、同じ仕事の中で直す（その repo の PR）。洗い出しだけで終わらせない。土台の PR は本文の「使う側の写しの残り」に、repo ごとの直しの PR か「なし（探した所）」を書き、その直しが全部合流するまで「終わった」と言わない。この窓から触れない repo は、原因の台帳の行にして repo ごとに 1 つの直す窓を `直す窓` に付ける。
- **main へ入れる** — 製品の repo（main へ入れると本番に出る物）も土台も、合流の前にオーナーへ「入れてよいですか」と聞かない。揃える物は 2 つ: ①書いた窓と別の窓のレビュー（合流の前に 1 回）が今の先端に green（red を直した後は同じレビューの窓の見直しで付ける） ②試験が緑で main との衝突が無い。全体の絵は設計の時に掘り下げる元の図（docs-kit:big-picture）で、合流の条件にしない。絵と違う・絵が無い・照らせないを理由に止めない。
- **設計図どおりかの照らし** — 合意した設計の仕事（案件・段の区切り）が全部終わった時に 1 回、AI が箱ごとに確かめ、完了の報告に「設計図どおり」か「差とその扱い」を 1 か所書く。PR ごとには照らさず、合意した絵の無い仕事は照らさない。作り方のずれは AI が設計どおりに直す（聞かない）。設計そのものを変える時だけ、絵に戻ってオーナーと合意し直す。
- **判定を頼む** — 書いた窓が PR に 1 つだけレビューの窓を立てて頼み、返しを受けて合流まで運ぶ。red を直したら新しいレビューの窓を立てず、同じレビューの窓へ `send_message` で見直しを頼む。
- **記録で確かめる** — 「確かめた」は申告でなく、後から誰でも読める記録（試験の結果・正しい道の証明・正本を読んだ出力）で示す。記録の無い確かめは未確認として書く。
- **別の道で確かめる** — 出した答えを、作った処理の出力や自分の報告で確かめない。生の正本（元のファイル・API・画面）を読んで照らす。
- **情報の取り方** — 結果は件数と失敗した物の ID だけ出す。50 件以上を見る時は script で数える。
