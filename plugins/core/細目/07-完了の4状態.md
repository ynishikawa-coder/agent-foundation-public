## 7. 完了の 4 状態

| 状態 | 意味 |
|---|---|
| 終わった | 終わりの条件と確かめの条件が全部そろった |
| 一部 | 合意した目標そのものが途中で止まった。済んだ物と残った物を書き、残りは原因の台帳の行にして引き継ぐ |
| 止めた | 決めた止まりの条件に当たって止めた |
| 続けられない | 技術・権限・構造の理由で続けられない |

- **書かない言い方** — 「ほぼ終わった」と書かない（4 つのどれかで言う）。

- **根治の終わり** — 根治の仕事は、合意した目標が済み、原因の台帳のうち元の相談がこの頼みで目標の中の行が全部 `直した` か `直さない` の時に「終わった」。目標の外の行は `オーナーの判断` で控え、終わりの報告の後に聞く（残っても「一部」にしない）。台帳を引いた結果（行の数と行き先ごとの数）を記録として報告に付ける。
- **穴の聞き方** — 終わりの報告は、まず頼まれた物が終わった事と、何が前→後に変わったかを書く。その後に、目標の外で見つけた穴ごとに 3 つ（何が穴か／放っておくと何が起きうるか／AI の案）を添えて「どうしますか」と聞く。同じ原因の穴は 1 つにまとめる。直す窓はオーナーが「直して」と答えた穴にだけ立てる。
- **土台の直しの終わり** — 土台を直す仕事は、使う側の repo（製品の repo を含む）に残った同じ決まりの写し・古い形を指す文も、同じ仕事の中で直す（その repo の PR）。洗い出しだけで終わらせない。土台の PR は本文の「使う側の写しの残り」に、repo ごとの直しの PR か「なし（探した所）」を書き、その直しが全部合流するまで「終わった」と言わない。この窓から触れない repo は、原因の台帳の行にして repo ごとに 1 つの直す窓を `直す窓` に付ける。
- **main へ入れる** — 製品の repo（main へ入れると本番に出る物）も土台も、合流の前にオーナーへ「入れてよいですか」と聞かない。揃える物は 3 つ: ①書いた窓と別の窓のレビュー（合流の前に 1 回）が今の先端に green（red を直した後は同じレビューの窓の見直しで付ける） ②試験が緑で main との衝突が無い ③作り終わりに、書いた窓と別の目が実物を、オーナーと合意済みの全体の絵と照らして差が無い。③で差が出たら main へ入れずに止め、差を見せてオーナーに決めてもらう（知らせて進めない）。全体の絵がまだ無い仕組みを直す時は、先に AI が絵を描いてオーナーの OK を取り、その絵と照らしてから入れる（絵が無いまま入れない）。
  - **③の照らし方** — 正本は review-pr 点 13。差なしは一言なしで入れ、差あり・照らせない（核 §7 の「照らせない時」）は止めて聞く。土台の plugin どうしの借りの流れは、書いた窓が土台の絵の版を上げて足す。
- **判定を頼む** — 書いた窓が PR に 1 つだけレビューの窓を立てて頼み、返しを受けて合流まで運ぶ。red を直したら新しいレビューの窓を立てず、同じレビューの窓へ `send_message` で見直しを頼む。
- **記録で確かめる** — 「確かめた」は申告でなく、後から誰でも読める記録（試験の結果・正しい道の証明・正本を読んだ出力）で示す。記録の無い確かめは未確認として書く。
- **別の道で確かめる** — 出した答えを、作った処理の出力や自分の報告で確かめない。生の正本（元のファイル・API・画面）を読んで照らす。
- **情報の取り方** — 結果は件数と失敗した物の ID だけ出す。50 件以上を見る時は script で数える。
